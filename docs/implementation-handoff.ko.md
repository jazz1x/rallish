# rallish — 구현 핸드오프

> Claude Code에서 구현을 시작하기 전에 먼저 읽을 것. 명세들을 묶어주는 진입점이며, *무엇을 만들지*(그건 링크된 명세에 있음)가 아니라 *어떻게 실행할지*를 정한다.
> **버전:** `VERSION`(0.3.0) 추종 · **최종 수정:** 2026-06-24 · [English](./implementation-handoff.md)

## 1. 인계받은 것

완결된 명세 세트. 의도는 이제 구현이 **설계가 아니라 실행**이 되는 것 — 빌더에게 필요한 모든 결정이 이미 적혀 있다. 다음 순서로 읽어라:

| 순서 | 문서 | 답하는 것 |
|------|------|-----------|
| 1 | `feature-spec.ko.md` | 무엇이 **연결됨** vs **선언만** vs **계획됨**인가 — 진실표. 이미 있는 걸 "구현"하지 않도록 여기서 시작. |
| 2 | `docs/reports/2026-06-23-production-readiness-gaps.md` | 티어별 갭 목록(Tier 0–3) — 이미 우선순위가 매겨진 **작업 큐**. |
| 3 | `test-plan.ko.md` | 완료 정의(DoD)와 각 기능이 가져야 할 정확한 테스트. |
| 4 | `performance-spec.ko.md` | 성능 목표 + 벤치마크 스위트 + 알려진 `lastHash` O(n) 리스크. |
| 5 | `user-manual.ko.md` | 사용자 관점의 동작 계약 — 너의 수용 렌즈. |
| 6 | `prd-cross-check-ping-pong.md` | 유일한 **계획됨** 기능(F22), 완전 명세됨. |
| — | `north-star.md` | *왜*와 해자(moat). 결정이 벤더 중립성·감사·게이트에 영향을 줄 때 참조. |

**시퀀싱은 이미 결정됐다 — 재계획하지 말 것.** `feature-spec.ko.md` §5("구현자가 인계받는 미결 항목")를 따르라. 감사 티어를 반영한다: Tier 1 첫 실행 UX → Tier 2 하네스 주장을 참으로 → Tier 3 신뢰 → 기능 작업.

## 2. 실행 가이드 — sonnet을 적재적소에 (맞는 곳에 맞는 도구)

이 작업은 병렬화가 잘 된다. 더 싸고 빠른 모델(Sonnet)을 넓고 잘 정의된 부분에 적극 투입하고, 한 수 잘못 두면 파급되는 소수 지점에만 깊은 추론을 아껴 써라.

**Sonnet을 적극·병렬로 투입할 곳:**

- **탐색·검색 팬아웃** — 호출 지점 매핑, 심볼 사용처 전수 조사, 코드 대조 검증. 읽기 전용 Sonnet 탐색기를 동시에 여러 개 띄워라.
- **`test-plan.ko.md` §5의 테스트 작성** — 이미 항목별로 명세돼 있음; 테이블 주도 테스트 생성은 정확히 Sonnet의 영역.
- **기계적·대량 편집** — 리네임, 문서/코드 주석 동기화, 플래그 도움말 워딩, `performance-spec.ko.md` §4.2의 벤치마크 스캐폴딩.
- **적대적 cross-check 리뷰** — 코드를 새로 읽고 변경을 **확증이 아니라 반증(falsify)**하려는 *탈상관(decorrelated)* Sonnet 리뷰어를 돌려라(이 명세 세트를 단단하게 만든 바로 그 방법). 너 자신의 작업에 적용한 cross-check ping-pong(F22).
- **번역·미러링** — `.md`와 `.ko.md` 쌍을 동기 유지.

**깊고 단일 스레드 추론(신중한 패스, 또는 더 강한 모델)을 아껴 쓸 곳:**

- **`pkg/contract`의 계약 변경** — SSOT다; 형태를 잘못 바꾸면 모든 소비자로 파급된다. `schema_version` 범프와 함께, 한 번에 신중히 바꿔라.
- **게이트 파이프라인과 안티스핀 불변식**(`internal/cycle/gates`, `stuck.go`) — 차별점; 미묘한 정확성, 조용히 약화되기 쉬움.
- **G6 액션게이트 강제 경계** — rallish는 *선언+기록*, 훅이 *강제*. 실수로 이 선을 넘으면 rallish가 실행자가 된다(north-star 위반).
- **A2A v1.0 / MCP 와이어 준수** — 엄격 파싱과 명명된 SSE 이벤트; 준수는 이진(binary)이다.
- **해자**를 건드리는 모든 것: 벤더 중립성, 변조 증거 감사, 게이밍 불가 게이트.

**항상:** 가장 싼 오라클이 정확성을 판정하게 하라 — 다시 읽지 말고 `make check-all`(자율 사이클이 돌리는 그 게이트)을 돌려라. 셀프 요약이 아니라 그린 게이트를 신뢰하라.

## 3. 효율 원칙 — 같은 일을 두 번(세 번) 하지 마라

> **최고의 효율은 같은 일을 두 번, 세 번 하지 않는 것.**

이건 구호가 아니라 rallish 자체의 설계 방식이며, 구현을 지배해야 한다. 구체적으로:

1. **단일 진실 출처 — 사실은 정확히 한 곳에서 바꾼다.** 계약은 `pkg/contract`에; 게이트 순서는 `StandardPipeline`에 단 한 번; config 기본값은 `internal/config`에 단 한 번. 사실을 파일 간에 포크하지 마라 — 같은 것을 두 번 고치고 있다면 빠진 SSOT를 발견한 것이다.
2. **기존 표면을 재사용하라; 평행한 것을 발명하지 마라.** cross-check PRD 자신의 가드레일이다(`Summary` / `Artifacts` / `TurnRecord` / 레저를 새 워크플로 그래프 대신 재사용). 필드·파일·타입을 추가하기 전에, 기존 표면이 이미 그걸 운반하는지 확인하라.
3. **다시 스캔하지 말고 캐시하라 — `lastHash` 교훈.** `performance-spec.ko.md` §7은 레저 append가 매 턴 파일 전체를 재독(O(n) → O(n²))함을 지적한다. 수정과 마인드셋은 같다: 재계산하지 말고 꼬리(tail)를 기억하라. 어디서나 적용하라 — 이미 아는 걸 재계산하는 건 일을 두 번 하는 것.
4. **한 번만, 탈상관으로 리뷰하라 — 그다음엔 게이트를 신뢰하라.** 네 서사를 보지 않은 리뷰어로 적대적 cross-check를 한 번 돌리고, 그들이 반증한 것을 고치고, 넘어가라. 이미 그린인 작업을 재리뷰하는 건 일을 반복하는 것.
5. **독립 작업은 병렬화; 진짜 의존만 직렬화.** 독립 과업(예: Tier 1 항목)은 동시 실행; 서로의 출력에 진짜 의존하는 단계만 사슬로 엮어라.
6. **정직한, 역량 게이트된 명명으로 재조사를 막아라.** 기능이 ○/◑ → ✅로 넘어가는 순간, *같은* 변경에서 `feature-spec.ko.md`의 성숙도 태그를 갱신하라. 낡은 태그는 다음 사람이 네가 이미 끝낸 걸 재감사하게 만든다 — 가장 비싼 종류의 반복 작업.

## 4. 자율 전달 루프 — 커밋 → PR → CI 그린 머지

각 작업 단위를 머지된 그린 PR까지 **자율적으로** 끌고 가라 — 사람의 게이트가 아니라 그린 게이트만. 아래 규칙은 모두 이미 레포에 인코딩돼 있다; 재발명하지 말고 따르라.

**1. 브랜치.** 피처 브랜치에서 작업, `main`/`master`에선 절대 금지(사이클 Preflight 게이트와 `CONTRIBUTING.md` 둘 다 강제; `main` 커밋은 거부됨).

**2. 의미 단위 커밋.** 커밋 하나에 논리적 변경 하나 — 거대한 단일 커밋도, 파일당 커밋도 아니다. 각 커밋은 독립적으로 리뷰 가능하고 트리를 그린으로 남겨야 한다.
- **컨벤셔널 커밋 접두사 필수**, `commit-msg` lefthook 훅이 강제: `feat: fix: refactor: docs: test: chore: sec: ci: build: perf: style:`. 접두사 없는 제목은 거부된다.
- **`--amend` 금지, `--no-verify` 금지** — 사이클 Commit 게이트와 같은 규칙. 훅이 핵심이다; 우회하지 마라.
- 의미 단위 커밋은 자기 문서를 동반한다: `CHANGELOG.md`(및 `CONTRIBUTING.md`에 따른 `.ko`/`.jp` 패리티 파일)를 갱신하고 관련 `feature-spec` 성숙도 태그를 **같은 커밋에서** 전환 → 변경이 자기완결적이고 재감사되지 않게.

**3. 푸시 전 로컬 게이트 — 단일 오라클.** `make check-all`(gofmt + `go vet` + `-race` 테스트 + `golangci-lint` + no-raw-ANSI 스윕) 실행. **CI를 정확히 미러**하므로, 그린 `make check-all`은 그린 CI의 예측이다. 그것이 이미 검사하는 걸 손으로 재검증하지 마라 — 그건 일을 두 번 하는 것(§3).

**4. `main` 대상으로 PR 열기.** `.github/PULL_REQUEST_TEMPLATE.md` 체크리스트 채우기(`go mod tidy` 클린, `go vet`, `go test ./...`, `golangci-lint`). 변경 유형과 테스트 방법 기술.

**5. CI를 그린으로 몰고, 그다음 머지 — 자율적으로.** `CI` 워크플로(`.github/workflows/ci.yml`)는 매 푸시·PR에서 `tidy`(`go mod tidy` + `git diff --exit-code`), `vet`, `lint`, 테스트/레이스 잡을 돌린다.
- **레드 머지 금지.** 잡이 실패하면 로그를 읽고, 또 하나의 의미 단위 커밋으로 **전진 수정(fix-forward)**, CI 재실행.
- 흔한 함정은 `tidy` 잡: `go mod tidy` 돌리고 바뀐 `go.mod`/`go.sum`을 커밋하지 않으면 `git diff --exit-code`가 실패한다.
- **모든** CI 잡이 그린이고 완료 정의(§5)를 만족하면 머지. 그린에 대해선 사람 승인 단계가 필요 없다 — 단, 레드이거나 DoD 미충족 PR은 **절대** 머지 금지. 하네스와 같은 규율이다: 검증자가 산출한 그린 신호만 신뢰하고, 워커는 그것을 위조할 수 없다.

이 전달 루프는 `cycle run --once`를 감싸는 바깥 래퍼다: 사이클 Commit 게이트가 이미 원자적·훅 준수 커밋을 만들고, 이 절은 그 위에 push → PR → 그린 머지를 더해 작업 단위가 감독 없이 안착하게 한다.

## 5. 완료 정의

변경은 `test-plan.ko.md` §8을 만족할 때 완료다: 테스트 존재(동시성엔 `-race`), 건드린 패키지 커버리지가 §4 바닥 유지, `make check-all` 통과, 계약 변경은 왕복 테스트 + `schema_version` 범프 동반, ✅로 이동한 기능은 `feature-spec.ko.md` 성숙도 태그 갱신 **그리고** 대응하는 갭 테스트를 pending→green으로 전환, 그리고 — §4에 따라 — 변경이 의미 단위 커밋으로 그린·머지된 PR에 안착할 때.
