# rallish — 구현 핸드오프

> 이 명세들을 Claude Code에서 받아 실제 코드로 만드는 엔지니어(또는 에이전트)를 위한 문서.
> **버전:** `VERSION`(0.3.0) 추종 · **최종 수정:** 2026-06-24 · [English](./handoff-implementation.md)

## 두괄식(BLUF)

구현에 필요한 모든 것은 이미 명세됐고 **코드와 대조 검증**됐다. 당신의 일은 만드는 것이지 다시 조사하는 것이 아니다. 네 개 명세를 읽고, 아래 티어순 작업계획에서 다음 항목을 골라, 알맞은 모델로 구현하고, 탈상관(decorrelated) Sonnet 검증으로 확인한 뒤, 성숙도 태그를 올린다 — 그리고 같은 질문을 두 번 건드리지 않는다.

## 단 하나의 규칙: 각 작업은 정확히 한 번만

**최고의 효율은 같은 일을 두 번, 세 번 하지 않는 것이다.** 이 핸드오프는 이미 아는 것을 다시 도출하지 않게 하려고 존재한다. 구체적으로:

- **조사는 끝났다.** `feature-spec.ko.md`가 모든 기능을 wired/declared 상태와 file:line 근거로 이미 매핑했고, 적대적 Sonnet 패널이 이미 코드와 교차검증했다. **성숙도 태그와 감사 티어를 진실의 출처로 신뢰하라.** 무엇이 빠졌는지 정하려고 코드베이스를 다시 감사하지 마라 — 답은 명세에 있다.
- **새로 읽지 말고 명세에서 빌드하라.** 아래 각 작업 항목은 feature-spec ID와 수용 기준을 가리킨다. 그 기준대로 구현하라. 명세가 틀렸으면 명세를 *한 번* 고치고 넘어가라 — 계속 재론하지 마라.
- **한 번 검증하고, 알맞은 리뷰어로, 닫아라.** Sonnet 리뷰가 통과하고 `make check-all`이 그린이면 항목은 끝이다. *같은* 변경에서 성숙도 태그(○/◑ → ✅)를 올려라. 나중에 "그냥 확인차" 다시 열지 마라.
- **산출물을 재사용하라.** 레저, contract 타입, 게이트 파이프라인, `fake` 어댑터가 이미 있다 — 새로 만들지 말고 확장하라. north-star는 워크플로 그래프 엔진의 재도입을 명시적으로 금한다.
- **rallish 자신이 경고하는 루프를 피하라.** rallish의 안티스핀 교리(G5)가 여기서도 작업 방법이다: 실제 진전을 내거나 멈춰라. 턴을 반복하고, 통과한 게이트를 재실행하고, 닫힌 항목을 재리뷰하는 것이 바로 하네스가 잡으려는 "ping-pong / 무진전" 낭비다.

같은 파일을 두 번 읽거나 같은 질문을 두 번째 하고 있다면, 멈추고 그 답을 명세에 적어 너도 다음 에이전트도 다시 값을 치르지 않게 하라.

## 모델 전략 — Sonnet을 적재적소에

작업에 모델을 맞춰라. Sonnet이 일꾼이고, 정말 어려운 추론에만 더 강한 모델을 아끼고, 조회엔 빠른 모델을 쓴다. 모든 것을 가장 비싼 모델로 돌리는 것 자체가 "일을 두 번 하는 것"이다 — 더 싼 모델이 정확히 끝낼 일에 예산을 낭비한다.

| 작업 | 모델 | 이유 |
|------|------|------|
| 대량 구현(배선, 게이트, CLI 플래그, 어댑터, 테스트, 번역, 기계적 리팩터) | **Sonnet** | 명세 주도 코딩에 충분히 강하고, 잘 명세된 80%에 빠르고 경제적. 기본값이다. |
| 완성된 변경의 병렬·탈상관 **검증**(코드가 명세와 맞나? 퇴행 없나?) | **Sonnet**(여럿, 병렬) | 독립 리뷰어 교차검증 — 이 문서들을 검증한 적대적 패널과 같은 패턴. 탈상관 > 비싼 단일 패스. |
| 모호한 **설계 결정**, 보안/위협모델 추론(G6 액션게이트 강제, PreToolUse 훅, A2A 인증), 횡단 **contract 변경** | **Opus**(더 강한 모델) | 잘못된 결정의 되돌림 비용이 큰 곳. 깊은 추론을 여기에, 한 번, 앞단에 써라. |
| 사소한 조회(심볼 X 어디? 이 플래그 기본값?) | **Haiku**(빠름) | 답은 이미 명세에 있다; grep에 큰 모델 태우지 마라. |

실전 원칙: **Sonnet으로 초안·빌드, Opus로 어려운 경계만 결정·검증, 검증 패널은 병렬 Sonnet 리뷰어로.** Sonnet이 정말 불확실할 때만 Opus로 에스컬레이션하고 — 그럴 땐 결정을 명세에 적어 다시 결정하지 않게 하라.

## 작업 계획 (티어순; 각 항목은 "한 번 읽고, 한 번 빌드")

감사 티어순 — 하네스 주장을 깊게 하기 전에 사용성을 먼저 출시. 각 항목: feature-spec ID → 그 명세의 수용 기준 → 권장 모델.

**Tier 1 — 첫 실행 UX(낯선 사용자도 성공):**
1. 어댑터 인증 사전점검 + 실행 가능한 에러; `doctor`가 인증 검증 — F4 / G-F4. *Sonnet.*
2. 무자격증명 스모크용 `fake-demo` 프리셋(또는 `--fake`) 출시 — F1 / G-F1. *Sonnet.*
3. `rally` 데몬 자동 기동 + 기본 join 타임아웃 — F2 / G-F2 (그리고 모순된 `doctor`/`bootstrap` 도움말 문자열 수정). *Sonnet.*
4. 오늘 동작하는 설치 경로를 문서 첫머리에; skills-registry 한 줄 설치를 확인하거나 제거 — F-install. *Sonnet.*

**Tier 2 — 하네스 주장을 참으로(차별점):**
5. G6 액션게이트 **강제**: PreToolUse 훅 배선 + 런북 출시(또는 README 주장 하향) — F13. **위협모델 + 훅 계약은 Opus**, 배선은 Sonnet.
6. Merkle 증명을 실제 경로(`gate verify` / 레저 감사)에 연결하거나 RFC 9162를 built로 표기하지 말 것 — F12. *Sonnet*(라이브러리 완성; 통합 작업).
7. `internal/logx`에 로그 시점 시크릿 마스킹 구현(또는 주장 제거) — F21. **마스킹 경계 설계는 Opus**, 구현은 Sonnet.
8. A2A v1.0 SSE 준수: 명명된 `event:` 줄 방출 + `sessionId` 채움, MCP 경로 미러 — F16. *Sonnet.*

**Tier 3 — 신뢰(실제 경로 테스트 + 배포 마무리):**
9. 게이트된 실제 어댑터 통합 테스트 1개; 게이트 파이프라인 + 자동목표 커버리지 상승 — test-plan §6. *Sonnet.*
10. CI 커버리지 바닥 강제 — test-plan §4/§6.3. *Sonnet.*
11. Homebrew tap 프로비저닝 — 감사 Tier 3. *Sonnet.*

**성능(병행):**
12. `lastHash` O(n) 재스캔 확인·수정(tail 해시 캐시); `BenchmarkStuck/*`·`BenchmarkLedgerAppend/*` 스케일링 벤치마크 추가 — performance-spec §4.2/§7. **동시성 하에서 수정이 올바른지 확인은 Opus**, 구현·벤치마크는 Sonnet.

**기능 작업(Tier 1 이후):**
13. Cross-check ping-pong(F22) — PRD §5 테스트 계획과 §7 수용 기준대로 빌드. **contract/intent 설계는 Opus**(바톤 스키마를 건드림), 어댑터/테스트는 Sonnet.
14. 스크래치패드 연결(F20); `strict_round_robin` / `last_writer_wins` 구현 또는 검증기가 거부하게(F6). *Sonnet.*

## 항목별 루프 (단일 패스, 재작업 없음)

1. **읽기:** feature-spec 항목 + 수용 기준. (코드베이스 전체를 다시 읽지 마라 — 명세가 필요한 파일을 인용한다.)
2. **결정:** 모호함은 Opus로 *한 번* 결정; 결정을 명세에 적기.
3. **빌드:** Sonnet으로 수용 기준대로; 기존 타입/레저/게이트 확장.
4. **테스트:** `test-plan.ko.md`대로(그리고 "pending/expected-fail" 갭 테스트를 그린으로 뒤집기).
5. **검증:** 병렬 Sonnet 패널로: 코드가 명세와 맞나? 퇴행 없나? `make check-all` 실행.
6. **닫기:** *같은* 변경에서 성숙도 태그(○/◑ → ✅)와 사용설명서 갱신(정직한, 역량 게이트된 명명). 다음 항목으로. 되돌아보지 마라.

## 변경별 완료 정의

`test-plan.ko.md` §8 미러: 변경된 동작엔 단위 테스트; 동시성 민감 변경엔 `-race` 테스트; 변경 패키지 커버리지가 바닥 위 유지; `make check-all` 통과; contract 변경엔 왕복 JSON 테스트와 형태 변경 시 `schema_version` 범프; ✅로 뒤집힌 기능은 갭 테스트가 그린 **그리고** 같은 변경에서 성숙도 태그 갱신.

## 자기 자신에게 적용(도그푸드)

이 repo는 멀티에이전트 하네스다 — 자신에게 써라. `pair-review`(planner/executor/reviewer)로 구현을 구동하고 자율 청크를 `cycle run --once`로 돌려 게이트 파이프라인·stuck 브레이커·레저가 네 작업을 지키게 하라. 적대적 리뷰어 패턴(탈상관 Sonnet 교차검증)은 이 명세들을 검증한 그 패턴이다 — 검증 게이트로 계속 써라.
